# GLM 512K 단독 기동 확인

2026-11-08 KST. 사용자는 먼저 GLM 기동 상태를 보고 Kanana 동시 실행을 결정하도록 요청했다. Kanana는 실행하지 않았다.

## 결과

GLM이 context 524,288, parallel 8로 정상 기동했다. direct health는 `ok/warming=false`, 기본 warmup은 `ready`, 추가 계산 smoke는 `5`를 반환했다. `/v1/models`의 `max_model_len=524288`을 확인했다. 큰 입력과 최대 동시성의 부하 검증은 수행하지 않았다.

| 항목 | dgx1 | dgx2 |
| --- | ---: | ---: |
| 약 195초 감시 중 최저 MemAvailable | 20.42 GiB | 22.65 GiB |
| 감시 후반 MemAvailable | 20.72 GiB | 22.96 GiB |
| Docker restart count | 0 | 0 |
| Docker OOMKilled | false | false |

두 노드에서 0.5초 간격으로 MemAvailable과 SwapFree를 기록했다. 기동 시작 이후 kernel journal의 `oom-kill`/`Out of memory: Killed process`, Docker 로그의 `CUDA error`/`NCCL error`/`out of memory`/`Traceback`/`fatal` 검색은 모두 0건이었다. LiteLLM `/health/readiness`는 HTTP 200, `healthy/db connected`였다. proxy 경유 모델 추론은 별도 검증하지 않았다.

## 적용한 시험 설정

[glm53-512k.env](glm53-512k.env)를 기동 프로세스의 exported environment로 적용했다.

- `CONTEXT=524288`, `CONTEXT_RETRY=0`
- `MEMORY_RESERVE_GIB=20`
- `PROMPT_CACHE_GIB=4`
- `MEMGUARD_FLOOR_GIB=8`, `MEMGUARD_HOLD_S=2`
- parallel 8, FP8 KV pages, DFlash2, vision 및 나머지 실행 인자는 기존 설정을 유지했다.
- image: `tensorfold-glm53-spark:8734689e7a73`
- 양쪽 image ID: `sha256:6f08848c663bdc3d60cacfc863c28f9764fb86ed0fd426abf25da0f44dc07e73`
- recipe commit: `13f2464ee84ab2b5dabf0bb264d1144b02cf5fb7`
- engine commit: `f350cd3ea253a042e205746928271f9d8f71a82d`

영구 설정 파일 `scripts/local.sh`와 기존 `scripts/gitops-preparation.env`는 수정하지 않았다. 새 프로세스는 512K 시험 설정으로 계속 실행 중이지만, 이후 일반 `start.sh`로 다시 기동할 때는 이 profile을 명시적으로 export해야 한다. 운영 설정 확정과 Kanana 추가 기동은 이번 작업 범위에서 제외했다.

## 실제 할당과 의미

dgx1 startup 로그:

- model 표기: 83.02 GiB
- KV pool: 2,050 pages × 512 rows = 1,049,600 rows, 약 6.24 GiB
- 동시 streams 8개, 추가 stream당 고정 메모리 417 MiB
- reserve 20 GiB를 제외한 room 10.7 GiB
- **실제 prompt cache 1.6 GiB**: 요청 상한 4 GiB보다 작다.
- 모델 load 시간: 103.2초, 단일 기동 관측

context는 요청 하나의 상한이고 공유 KV pool은 여러 window를 확보하므로, context를 반으로 낮춰도 pool은 기존 6.25 GiB에서 6.24 GiB로 거의 줄지 않았다. 이번 가용 메모리 증가는 주로 reserve 증가와 prompt cache 축소에 따른 것이다. 이전 약 11.8 GiB보다 작은 cache 때문에 반복 대화의 재계산이 증가할 수 있으나 성능 비교는 수행하지 않았다.

이전 Kanana 단독 시험의 로딩 순간 추가 시스템 메모리 15.42 GiB를 현재 dgx1 가용 20.72 GiB에서 빼면 약 5.30 GiB다. 이는 공존 실측이 아닌 단순 예산 추산이며, framework 시작 등의 추가 비용도 포함하지 않는다. 8 GiB 중단 기준보다 낮으므로 이 상태에서 Kanana를 추가 기동하지 않고 사용자 판단을 기다린다. 실제 최대 입력 처리 시 여유는 아직 검증하지 않았다.

## 중단 기준과 복구 경로

- 기동 중 각 노드의 독립 감시 프로세스가 MemAvailable < 8 GiB이면 새 GLM을 중지하도록 했다. 기준 도달은 없었다.
- 정상 기동 뒤에는 recipe의 memory guard가 양쪽 노드를 감시하며 8 GiB 아래 상태가 2초 지속되면 중지하도록 설정되어 있다. 표본 간격과 실제 중지 지연이 있으므로 OOM 방지를 보장하는 장치는 아니다.
- 기존 1M 컨테이너는 양쪽 모두 `glm53-spark-before512-20261108` 이름으로 중지 상태로 보존했다.
- 실패 자동 복구 wrapper는 새 기동 실패 시 새 컨테이너를 중지·이름 변경한 뒤, 기존 컨테이너 이름을 `glm53-spark`로 되돌리고 worker→leader 순서로 시작하도록 준비했다. 이번 기동은 성공해 복구를 실행하지 않았다.
- 원래 설정과 기존 inspect, 시험 profile, 시작 로그, memory JSONL 및 kernel/Docker 확인 로그는 각 노드 `/home/USER/glm512k-check-20261108/`에 보존했다.
- 양쪽 raw 사본은 dgx1 `/home/USER/ds4/results/glm53-memory-20261108-13f2464-512k/`에 보존했다.
